# Alex v0.12 — simulation acceptance, evidence, and strict Nav2 parameters

> **Status: implemented + 90 automated tests passing locally; live ROS2/Gazebo runtime NOT validated.**
> v0.12 adds an opt-in acceptance harness for Ubuntu 24.04 / ROS 2 Jazzy / Gazebo Harmonic. This is **simulation-only** and must never connect to a real robot or motor driver.

## Why this batch exists

v0.11 created ROS/Gazebo models, map, and bringup, but CI runs without ROS 2. Static world validation cannot prove that LiDAR publishes, `/tf` is connected, AMCL localizes, or that Nav2 moves a differential-drive model. It also had two possible live-integration faults: a one-shot initial-pose publisher could use wall time when Nav2 runs with sim time, and flat Nav2 tuning may not reliably target the nested ROS node parameters. v0.12 replaces those paths with explicit configuration and a live acceptance tool that **fails closed**.

## New pieces

- `robotics/ros2/alex_sim/alex_sim/nav2_tuning.py`: generate validated, nested Nav2 parameters from the **installed Jazzy** defaults. Explicitly configure AMCL to use `base_link`, `odom`, `/scan`, and the initial pose at the dock `(0.7, 2.8)` in sim time; tune the existing controller/checker/costmap params without changing plugin identities. Missing expected nested paths are an error, not silent success.
- `robotics/ros2/alex_sim/alex_sim/acceptance.py`: ROS-free independent goal/TF evidence contract. Tests reject a successful Nav2 status if TF is stale, pose is out of tolerance, or feedback is absent.
- `robotics/ros2/alex_sim/scripts/ros_smoke.py`: live ROS graph probe and 3-leg navigation test. Graph must have **advancing `/clock`**, `/scan`, `/odom`, `/map`, `map -> odom -> base_link -> lidar_link`, a fresh `map -> base_link` TF and a ready `NavigateToPose` action.
- `scripts/run-ros-acceptance.sh`: explicit opt-in, isolated local ROS discovery on domain `77`, launches Gazebo/Nav2 in its own process group, records launch log, runs three goals, and tears down the process group on exit.
- `scripts/ros-preflight.py`: read-only runtime dependency/flag check. The resulting JSON says `blocked` when ROS is not installed and **never** claims runtime acceptance.
- `tests/v12.test.mjs` + `tests/fixtures/nav2-jazzy-minimal.yaml`: offline checks for nested parameter generation, fail-closed behavior, route coordinates, independent pose verification, and script gates.

## ROS-free verification (any development machine)

```bash
npm install
npm test                 # 90 test cases at v0.12 on local development runtime
npm run sim:check        # world/map/robot/static protocol validation, NO ROS run
npm run sim:preflight    # writes .local/ros/preflight.json, may say BLOCKED
```

`sim:check` **cannot** substitute for the following live commands.

## Live acceptance on dedicated Ubuntu 24.04 + ROS 2 Jazzy / Gazebo Harmonic

Use an **isolated simulation workstation** with a supported graphical/GPU/EGL setup for Gazebo's GPU LiDAR. Ensure Nav2 Jazzy, `ros_gz_sim`, `ros_gz_bridge`, `robot_state_publisher`, `tf2_ros`, `nav2_msgs`, `colcon`, `rclpy`, `python3-yaml` and related packages are installed. Do not connect any real ROS-controlled robot on the same host/domain.

```bash
source /opt/ros/jazzy/setup.bash
export ALEX_ROS_SIMULATION_ONLY=1
export ALEX_RUN_ROS_INTEGRATION=1
export ROS_DOMAIN_ID=77
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
npm run sim:preflight
npm run sim:accept
```

Expected real-success evidence:

- `.local/ros/acceptance-launch.log`: Gazebo, bridges, Nav2 and AMCL logs;
- `.local/ros/acceptance-report.json`: `"status": "passed"`, required graph checks and **three verified legs**;
- For each leg, Nav2 action must report `SUCCEEDED`, at least one valid feedback sample must arrive, **odometry must show actual travel on nontrivial legs**, and a **fresh independent map-frame TF** must show the robot within **0.12m** of the named target;
- The three legs are **dock → study desk (1.7,1.6) → story corner (4.9,1.7) → dock (0.7,2.8)**. These target coordinates come from `src/robot/map.ts`'s 0.1m grid.

If any stage fails, the script exits nonzero and the report contains a failure reason. **Do not claim a passing simulator until a real ROS 2 run produces this report**. The position tolerance is a simulation acceptance target, not a hardware safety guarantee.

### Staged debugging without passing acceptance

With `ALEX_ROS_SIMULATION_ONLY=1`, run `ALEX_WITH_NAV2=false npm run sim:launch` to inspect basic Gazebo and bridge topics. In a second terminal, source ROS Jazzy and `.local/ros/install/setup.bash` and run `ros2 topic echo /scan --once`, `ros2 topic echo /odom --once`, `ros2 run tf2_ros tf2_echo odom base_link`, and `ros2 topic hz /clock`. These are diagnostic steps only.

To run the graph-only smoke manually, first source the ROS overlay and use the same environment variables in both terminals, then `npm run sim:smoke`. `npm run sim:smoke -- --navigate` runs a single desk goal, while `npm run sim:smoke -- --route` runs the round trip. Do not run concurrent goal producers against the simulator.

## Explicit non-goals and limitations

- Not a real Nav2 acceptance result: **no ROS 2, Gazebo, Docker or GPU was available in the current execution environment**. A local `blocked` preflight is evidence of this limitation, not a failed navigation test.
- Not a real-robot controller or safety-certified stop: Nav2 cancellation and killing Gazebo are not physical emergency stops. No hardware `/cmd_vel` bridges, GPIO, motors or direct actuation.
- This version does not include localization calibration against real sensors, stairs/fall detection, obstacle safety certification, or automatic obstacle-avoidance testing with dynamic humans.
- ROS Jazzy `nav2_bringup` default parameters may vary by installed patch release; the strict generator rejects an incompatible structure instead of assuming success.

## Follow-up after obtaining a real ROS run

Prioritize fixing any observed actual startup/TF/QoS/physics/Nav2 errors from `.local/ros/acceptance-launch.log`; then rerun `sim:accept` and inspect the resulting JSON. Only then consider simulation CI with a dedicated ROS runner, more realistic dynamic obstacles, or physical robotics.
