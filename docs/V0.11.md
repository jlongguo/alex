# Alex v0.11 — reproducible Gazebo + ROS 2 Jazzy simulation scaffold

> **Status: assets + launch/configuration + static CI + opt-in real ROS smoke test.**
> The current automated environment has **no ROS 2, Gazebo or Nav2 installation**; no claim of successful physics navigation or real Nav2 integration is made. **SIMULATION ONLY. No real robot or motor driver.**

## Scope

- Source-of-truth `src/robot/map.ts` generates the Gazebo world and ROS Nav2 occupancy map. **Do not hand-edit generated `worlds/alex_home.sdf`, `maps/alex_home.pgm`, or `maps/alex_home.yaml`.**
- Differential-drive robot `models/alex_bot/model.sdf`: 2 independently actuated Gazebo wheel joints, passive caster, GPU lidar, Gazebo DiffDrive odometry and simulated `/cmd_vel` input. `urdf/alex_bot.urdf` provides ROS visualization + static `base_link -> lidar_link` transform.
- Simulated bridge: `/clock`, `/scan`, `/odom`, `/tf` from Gazebo into ROS; `/cmd_vel` from ROS into **Gazebo only**. `robot_state_publisher` publishes fixed transforms.
- Optional `nav2_bringup`/AMCL with a map generated from the canonical grid, using Jazzy's installed default Nav2 parameters plus small robot-specific overrides.
- `scripts/ros_smoke.py` checks topics, TF and Nav2 Action availability, optionally sending a goal **inside Gazebo**. Requires explicit opt-in; runs **only after** the simulator is launched.

## Map contract

The TypeScript grid is **60 columns × 34 rows**, `0.1m` per cell, map origin `(-0.05,-0.05,0)`. Gazebo `+x/+y` correspond to grid `+x/+y`, with no implicit screen-y inversion. Occupancy map origin is a half-cell negative offset, so the **center** of grid cell `(i,j)` is exactly `(0.1*i, 0.1*j)` in ROS/Gazebo meters. PGM rows are written in reverse y order because image row 0 is the top. Only TS `occupied(x,y)` determines cells marked occupied (includes simulation clearance), while 3D collision geometry uses the exact walls/furniture rectangles.

| Location | Grid | ROS map-frame goal (meters) |
| --- | --- | --- |
| Dock / spawn | `(7,28)` | `(0.7,2.8)` |
| Study desk | `(17,16)` | `(1.7,1.6)` |
| Sofa | `(32,16)` | `(3.2,1.6)` |
| Story corner | `(49,17)` | `(4.9,1.7)` |

Nav2's dynamic costmap may produce a **different** route than grid A*, due to footprint, inflation, physics and localization. Do not expect identical paths. The v0.10 adapter still requires a verified pose within 0.05m of the goal; action success alone is insufficient.

## Real ROS 2 / Gazebo test on Ubuntu 24.04 (not run in this CI)

Required: ROS 2 Jazzy, Gazebo Harmonic, `ros_gz_sim`, `ros_gz_bridge`, `robot_state_publisher`, Nav2 (`nav2_bringup`, `nav2_common`, `nav2_msgs`), `colcon`, `rclpy`, Python `yaml`, and a supported GPU/EGL or graphical environment for Gazebo's `gpu_lidar`. Confirm specific package names and versions on your machine with ROS/Gazebo upstream installation instructions.

```bash
source /opt/ros/jazzy/setup.bash
export ALEX_ROS_SIMULATION_ONLY=1
export ROS_DOMAIN_ID=77          # isolate from other ROS domains/devices
npm run sim:launch              # builds alex_sim ament package; Gazebo + AMCL/Nav2 by default
```

In another terminal, while the simulation is running:

```bash
source /opt/ros/jazzy/setup.bash
source .local/ros/install/setup.bash
export ALEX_ROS_SIMULATION_ONLY=1
export ALEX_RUN_ROS_INTEGRATION=1
export ROS_DOMAIN_ID=77
npm run sim:smoke               # /clock, /scan, /odom, /map, TF and NavigateToPose check
npm run sim:smoke -- --navigate # also submit study desk goal and require Nav2 succeeded
```

For world / robot / bridge inspection without Nav2, set `ALEX_WITH_NAV2=false` before `npm run sim:launch` and inspect `/clock /scan /odom /tf`. This **does not** pass the Nav2 smoke test; it is just a staged debugging mode.

To connect the v0.10 Alex virtual-device client to this *same* Gazebo ROS domain, follow `docs/V0.10.md`: start authenticated Alex locally, pair a virtual device, approve only its `sim.navigation.goto` capability, then run the virtual device with `ALEX_NAV_BACKEND=ros2`, `ALEX_ROS_SIMULATION_ONLY=1` and the test domain. No physical robot or device-control endpoints are provided.

## Safety and limitations

- Launch **refuses** to proceed without `ALEX_ROS_SIMULATION_ONLY=1` and ROS 2 Jazzy. Choose an isolated ROS domain and never bridge these topics to a physical robot.
- `Nav2` goal cancellation is not an emergency stop. The simulator is not validated for household obstacle avoidance, children or real actuation.
- The prebuilt `Nav2` configuration is derived from installed Jazzy default parameters and should be tuned on an actual Gazebo run (footprint, inflation, MPPI control, map localization). The static validator cannot catch missing plugins, SDF physics instability, sensor QoS mismatches, or Nav2 runtime TF errors.
- Potential `gpu_lidar` headless rendering requirements may need a GPU / EGL environment; use a graphical Ubuntu workstation for first integration if headless `/scan` does not publish.
- The optional smoke script requires genuine ROS middleware; it is **not** run by the normal Node unit tests. Do not mark live navigation complete until this passes on a ROS machine and pose/obstacle traces are examined.
