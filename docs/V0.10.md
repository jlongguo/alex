# Alex v0.10 — experimental ROS 2 / Nav2 simulation adapter

**Scope: Gazebo/ROS 2 simulation only. Physical motor control is not supported or safe.**

## Architecture

The Alex v0.9 grid simulator remains the default. `ALEX_NAV_BACKEND=ros2`
selects `Nav2SimulationBridge` inside the **virtual device**. It launches a
short-lived Python `rclpy` `NavigateToPose` ActionClient over a private
newline-delimited JSON stdin/stdout channel (no shell or arbitrary commands).
The child requires a ROS `/clock`, obtains `/navigate_to_pose`, sends one
allowlisted target pose in frame `map`, forwards pose/distance feedback,
and requests action cancellation when Alex cancels a job.

```
Alex Plan/Workflow -> DeviceGateway -> SSE virtual-device
                                            | (default) GridNavigationBridge
                                            | (optional) Nav2SimulationBridge
                                                       | JSONL subprocess
                                                nav2_action_client.py
                                                       | ROS Action
                                                /navigate_to_pose (Gazebo)
```

The existing gateway protocol v2 persists authenticated `planning`, `moving`
and `arrived` telemetry, checks increasing sequences and target proximity,
then accepts successful completion only after arrival evidence. The new
adapter converts meters to the existing fictional 0.1m-per-cell grid.
**The ROS map coordinate origin, axes, obstacles and named target positions
must match `src/robot/map.ts` exactly.** Merely installing Nav2 is not enough.
Do not connect the adapter to a different ROS map or real robot.

## Use

1. Start a compatible ROS 2 Jazzy/Nav2 Gazebo simulation with `/clock`,
   `/navigate_to_pose`, and an Alex-aligned `map` frame. Verify it separately
   with ROS tooling. This repository does **not** yet include a Gazebo world,
   robot URDF or Nav2 configuration.
2. Run Alex as before with `AUTH_MODE=local`, pair a virtual device and have
   the parent explicitly approve `sim.navigation.goto`.
3. Launch the virtual device with both flags:

```bash
ALEX_NAV_BACKEND=ros2 ALEX_ROS_SIMULATION_ONLY=1 \
  ALEX_DEVICE_ID='dev-...' ALEX_DEVICE_TOKEN='...' \
  npm run virtual-device
```

The `python3` process must have `rclpy`, `nav2_msgs`, `action_msgs`,
`geometry_msgs`, and `rosgraph_msgs` on its ROS environment path. If no valid
ROS simulation/action server is present, it fails closed; no grid fallback
is attempted when ROS2 is explicitly selected. There is no direct velocity
or motor-control endpoint.

## Protocol

Input from Node: `{"type":"navigate","goal":{"destination":"study_desk","frame_id":"map","x":1.7,"y":1.6,"yaw":0}}`.

Actions from Node: `{"type":"cancel"}`.

Child events: `{"type":"ready"}`, `{"type":"feedback","distance_remaining":0.5,"pose":{"x":1.6,"y":1.6,"yaw":0}}`,
`{"type":"result","status":"succeeded"}` (or failed/rejected/cancelled).

The Node bridge validates message bounds and maps positions to grid cells,
requires the final observed pose to be within **0.05m** of the approved target,
and never synthesizes an arrival just because an action reports success.
This tolerance is intentionally strict for the fictional world; adjust only
after building a matching simulator and validating real action tolerances.

## Reliability and safety boundaries

- A child process crash, missing `/clock`, unavailable action server, malformed
  response, late/stale feedback, bad location or no proof of arrival fails the
  task. Permission withdrawal and cancellation block downstream skills.
- Cancellation is **best effort**, not an independently enforced emergency
  stop. Killing the action-client subprocess may **not** cancel a Nav2 goal;
  do not rely on this for physical safety. Physical platforms require
  independent local safety hardware and a verified ROS action lifecycle.
- Parent review, allowlisted destinations, per-device credentials and
  gateway task expiry remain enforced. ROS nodes themselves have their own
  security/domain configuration; avoid untrusted LAN access.
- Startup/goal/cancel deadlines are bounded. No interrupted navigation is
  automatically replayed after restart.

## Verification

`npm test` includes the previous 68 tests plus six new v0.10 tests using a
JSONL fake action server (simulation-only mapping, verified arrival, spoofed
arrival denial, rejection, cancellation, overlapping goals). Python source
syntax checked with `python3 -m py_compile` (does not validate ROS2 execution).

**Not validated:** real ROS 2 Jazzy/Nav2/Gazebo, navigation dynamics,
transform accuracy, physical localization, E-stop or certified motor safety.
The next required task is a reproducible Gazebo world/URDF/Nav2 launch setup
and an actual ROS2 integration test that is skipped unless the simulator is
present.
