# Alex v0.5 — Device Gateway and multi-device virtual runtime

## Scope

This release builds a **simulation-only** device command gateway between the Home Core and independently paired virtual devices. It cannot command GPIO, motors, real speakers, cameras, household locks or other physical actuators.

- The existing built-in 2D robot and `/api/tasks` remain unchanged.
- `DeviceRegistry` stores reported vs parent-approved capabilities separately.
- A device connects with an **independent bearer token** issued by parent-approved one-time pairing.
- Devices send a heartbeat and receive virtual tasks via a long-lived authenticated **SSE** stream. A token-protected GET poll endpoint provides a fallback.
- Devices send `running` / `succeeded` / `failed` feedback via authenticated POST. Results are persisted; parent can cancel outstanding work.
- Job creation requires verified parent session, approved capability, recent heartbeat and a validated, small parameter schema.
- On reboot, queued/running work becomes `stopped` and **is never replayed automatically**.
- On credential revocation, device command stream is closed and unfinished work is stopped.
- `deviceId` in `/api/command` allows the opt-in AgentProvider to propose a destination for an external virtual device. Parent permissions and strict capability validation still apply.

## Separation of trust

The model is not an authority. A model's structured navigation proposal is untrusted and is checked by the gateway, which only recognizes `sim.navigation.goto`. All other external capabilities remain virtual presentations (`display.face`, `audio.output`). A `succeeded` result means a virtual device process reported completion; it is NOT proof of real-world movement.

## Running two local virtual devices

1. Set `AUTH_MODE=local`, a strong `ALEX_PARENT_PASSWORD` and a unique `ALEX_CHILD_PIN`; run `npm test` and `npm start`.
2. Log into the local console as parent. In **多设备任务派发** enter a name and press **配对新虚拟设备**. Copy the one-time terminal command shown in the UI. Alternatively, POST `/api/devices/pair/start` with the parent session cookie, then use the returned one-time code with `/api/devices/pair/complete`. The second endpoint does not require a browser session, but the code must originate from an authenticated parent. Codes expire after 5 minutes.
3. In a separate terminal, launch the virtual device process (the token is given via environment, not committed to Git):

   ```bash
   ALEX_DEVICE_ID='dev-...' ALEX_DEVICE_TOKEN='...' npm run virtual-device
   ```

4. The simulator announces `sim.navigation.goto`, `display.face`, `audio.output` and sends heartbeats. As the parent, approve only the desired subset via `/api/devices/capabilities/approve` or the Web Console's *批准虚拟能力* control.
5. Dispatch a simulated navigation task via the console or `POST /api/gateway/dispatch` with a unique `requestId`. Watch it progress in `/api/gateway/jobs` and the simulator terminal.
6. Repeat steps 2–5 for another local virtual device. Each has its own token, status and inbox.

Recommended for manual API tests: use an API client or browser DevTools on `http://127.0.0.1:4317`; session cookies are HTTP-only. Never place tokens in query strings or code repositories.

## API reference

| Endpoint | Auth | Purpose |
| --- | --- | --- |
| `POST /api/devices/pair/start` | Parent session | One-time pairing challenge |
| `POST /api/devices/pair/complete` | Challenge code | Register virtual device; token returned once |
| `POST /api/devices/capabilities` | Device bearer | Declare virtual capabilities, `protocolVersion: 1` |
| `POST /api/devices/capabilities/approve` | Parent session | Authorize declared subset |
| `POST /api/devices/heartbeat` | Device bearer | Mark device recently connected |
| `GET /api/gateway/stream?deviceId=...` | Device bearer | Authenticated SSE virtual task feed |
| `GET /api/gateway/poll?deviceId=...` | Device bearer | Fetch pending virtual tasks |
| `POST /api/gateway/result` | Device bearer | Report job state transition |
| `POST /api/gateway/dispatch` | Parent session | Queue validated virtual task |
| `POST /api/gateway/cancel` | Parent session | Stop outstanding job |
| `GET /api/gateway/jobs` | Parent session | Inspect persisted jobs |
| `POST /api/command` with `deviceId` | Parent session | Provider-proposed virtual navigation |

### Example bodies

```json
{"deviceId":"dev-...","capabilities":["sim.navigation.goto","display.face"],"protocolVersion":1}
```

```json
{"deviceId":"dev-...","capability":"sim.navigation.goto","params":{"destination":"study_desk"},"requestId":"demo_task_20261103_00001"}
```

```json
{"deviceId":"dev-...","jobId":"job-...","status":"running"}
```

## Guardrails and known limitations

- This server **only binds to localhost**. There is no TLS transport, service discovery, LAN deployment support, firmware update, device attestation or end-to-end motor control.
- Device capability declarations do not automatically authorize operations. Parent approval is required. However, a compromised device token could still send forged virtual status updates for its own jobs.
- In-progress jobs are not resumed after restart; offline work is stopped after heartbeat loss/timeout. `audio.output` only prints text in the virtual client; it is not real TTS.
- Child roles cannot dispatch virtual tasks, inspect the private gateway task log, approve capabilities or access device credentials.
- Device tokens are stored as hashes, never exposed on `/api/devices`, `/api/privacy/export`, `/api/gateway/jobs` or audit logs.
- JSON state files are a local prototype, not a transactional production database. No multi-process server scaling or hard real-time guarantees.
- The 2D built-in robot is separate from external virtual clients. The simulator's remote `sim.navigation.goto` reports synthetic completion, not A* or Nav2 physical navigation.
- A future real robot adapter requires independent motor control safety, fail-safe remote stop, hardware-specific tests and child-safe certifications; **do not map `sim.navigation.goto` directly to physical movement**.
