# Alex v0.9 — grid navigation simulation and authenticated feedback

## Implemented
- GridNavigationBridge uses the existing A* model and steps through 2D grid coordinates, posting pose and progress; no physical robot is involved.
- Paired virtual clients announce protocol v2 and send authenticated navigation feedback to the hub.
- The gateway enforces job/device binding, explicit parent-approved capability, strict sequence/progress, map version, pose bounds and named-destination arrival before accepting v2 simulated navigation success.
- A virtual device may report cancelled/failed simulated tasks; a server restart always marks incomplete jobs stopped, with no automatic movement replay.
- The parent-only navigation-map and jobs APIs drive the console view of the fictional home.

## Local test
```bash
npm install
npm test
AUTH_MODE=local ALEX_PARENT_PASSWORD='unique-long-password' ALEX_CHILD_PIN='unique-pin' npm start
```
Open http://127.0.0.1:4317 and sign in as parent. Pair a virtual device, launch the displayed command in another terminal, approve its navigation capability, and dispatch a goal. Optional `ALEX_SIM_STEP_MS` slows simulated movement; `ALEX_SIM_OBSTACLE=1` adds a fixed virtual obstacle.

## Protocol v2
- `POST /api/devices/capabilities`: `{deviceId,capabilities:['sim.navigation.goto'],protocolVersion:2}` authenticated with device bearer token.
- `POST /api/gateway/telemetry`: `{deviceId,jobId,sequence,phase,progress,pose:{x,y,heading},mapVersion:'alex-home-grid-v1'}`. Device-authenticated, approved, monotonically sequenced, progress 0–100.
- `POST /api/gateway/result`: success for v2 navigation requires prior persisted arrival feedback.
- `GET /api/gateway/navigation-map`: local parent-only map snapshot.

## Safety boundaries
This is NOT a physical robot, ROS 2/Nav2/Gazebo connection, SLAM, verified localization or physical collision protection. The grid is fictional; device-reported poses are not trustworthy physical measurements. Never connect these APIs directly to motors. A future robotic adapter requires independent local watchdogs, emergency stop and hardware safety constraints.
